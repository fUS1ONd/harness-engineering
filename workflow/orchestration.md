# Оркестрация в T3 Code и работа с делегатами

Репозиторные правила конкретного проекта могут уточнять этот документ (например, пороги параллельности или команды сборки), но не отменяют базовую дисциплину T3 Code.

## Ветки и worktree

- Работа над усилием идёт в **одной интеграционной ветке**; в конце открывается один PR в целевую ветку (например, `dev` или `main`).
- Исполнитель запускается в изолированном worktree (`delegate_task` с `isolation: "worktree"`).
- Стартовый `cwd` в T3 — вне репозитория, поэтому **каждую** команду `run_command` начинать с `cd <путь_к_worktree> &&`.
- Новый worktree создаётся от HEAD корня проекта, а не от ветки усилия. Первый шаг брифа исполнителя — подтянуть ветку усилия (`git fetch <путь_к_worktree_усилия> <ветка>:<ветка>`) и убедиться, что он на её базе (`git merge-base --is-ancestor ...`), иначе `git reset --hard <ветка>`.
- Вливание в ветку усилия делает оркестратор через `git merge --ff-only` после rebase исполнителя. Сразу после вливания удалять временный worktree и ветку `t3/*`, а дочерний тред закрывать через `t3_thread_organize{action: "settle"}`. Для типового цикла слияния используй executor-driven капсулу `capsules/land-ticket` через `scripts/skillcache-run run /root/harness-engineering/capsules/land-ticket --state <path/to/state.json> '<JSON>'` (подробности — [capsules/README.md](../capsules/README.md)); при конфликте или падении проверок раннер деоптимизирует только упавший шаг и продолжит план после `continue`. Проверить забытые влитые worktree и ветки в любом репозитории можно скриптом `scripts/worktree-audit.sh <путь_к_репо>`.

## Дисциплина `delegate_task` и фоновые задачи

- **Фоновые задачи (`background-wait.py`):** в `~/.gemini/config/hooks.json` работает глобальный `Stop`-хук `background-wait.py` (потолок 15 мин, `timeout: 930`), который при `fullyIdle: false` удерживает ACP-ход открытым до завершения не-демон фоновых задач Antigravity (`run_command > 10s` по PID дочернего процесса `agy-real`, нативные `invoke_subagent`/воркфлоу) и возвращает `continue` с живыми правами T3 Code. Демоны (`IsDaemon: true`) игнорируются; при превышении 15 мин хук один раз просит агента сообщить статус/лог и отпускает ход.
  - Если `run_command` ушла в фон (`RUNNING` / `task-*`), завершай ход без поллинга `manage_task` — хук дождётся завершения и автоматически продолжит ход.
  - Внутри делегата по-прежнему предпочитай быстрые точечные проверки (`WaitMsBeforeAsync: 10000`), а полный прогон тестов и сборки делай на итоговом коммите перед вливанием (при этом долгие команды больше не обрывают `delegate_task` раньше времени).
- Временные файлы и скриншоты для `read_file` сохранять внутри worktree (удаляя до `git commit`) или в `brain/<id>/scratch/`, никогда в `/tmp`.
- Вместо `git commit --amend` делать новый коммит или `git reset --soft HEAD~1 && git commit -m ...`.
- Ожидание PR и тредов вести через `watch_pull_request` и `t3_thread_wait`, без `schedule` и без циклов `sleep`.

## Лимиты, модели и утилиты хоста

- Выбор моделей: оркестрация (`gemini-4-neon`), редактура, сложная архитектура и вся верификация/ревью (`gemini-4-neon` `"medium"` для потикетных `Standards`/`Spec`, `"high"` на сложных, `gemini-4-carbon` `"high"` для `final-code-review`) — на Google Gemini 4 (`antigravity`); `gemini-4-argon` и `gemini-4-carbon` `"low"` не используются. Для простых и дефолтных задач реализации — DeepSeek V4.1 Flash (`opencode`, `deepseek/deepseek-flash`, `variant: "high"`) с обязательной верификацией моделями Antigravity по `/root/.gemini/config/skills/vybor-modeli/SKILL.md`.
- Контроль контекста и эстафета (`~200k`): в `~/.gemini/config/hooks.json` работает автоматический синхронный `PreInvocation` хук `context-guard.py` (175k — предупреждение, 200k — стоп-лимит, 260k — аварийная остановка). При достижении ~200k агент записывает состояние в `hod.md` (внутри worktree / `.scratch/`, не коммитить), запускает преемника через `t3_thread_launch` с брифом и ссылкой на `hod.md`, а **преемник первым делом закрывает старый тред** (`t3_thread_organize{action: "settle", threadId: "<старый тред>"}`). Перед каждой волной дополнительно проверяй остаток квоты через `ctx`.
- Утилиты хоста: искать по коду через `rg` или `git grep` (в `grep` флаги `-B/-A` ставить до `--`); шаги GitHub Actions смотреть через `gh run view <id> --json jobs`, сырые логи — с `--allow-escape-sequences`; многострочный Python запускать через `python3 - <<'EOF'`.

## Ревью и гейт качества

- Перед запуском ревьюеров оркестратор проверяет `git -C <wt> status --porcelain` (пусто) и `git -C <wt> rev-parse HEAD`.
- Ревью тикета идёт по двум осям (`Standards` и `Spec`, скилл `code-review`) против спеки, тикета и `CODING_STANDARDS.md` целевого репозитория.
- Итоговое ревью ветки — независимый проход `final-code-review` на сильной модели.
- **Жёсткое правило для ревьюера:** любое решение в виде костыля, обходного таймера, молчаливого проглатывания ошибки или «оправдательного» комментария вместо фикса первопричины — **повод завернуть PR**.
